# Adding a domain : DNS records and full procedure

How to hook a new domain (DNS hosted anywhere : Cloudflare, OVH, Gandi, Route53,
...) to this mail server so it can send and receive mail with passing SPF / DKIM
/ DMARC.

This doc uses `example.com` as the domain and the following placeholders ; swap
them for your real values everywhere :

| Placeholder       | What it is                                          | Example                  |
|-------------------|-----------------------------------------------------|--------------------------|
| `<DOMAIN>`        | The domain you want to host mail for                | `example.com`            |
| `<MAIL_HOST>`     | Public hostname of the mail server (A record)       | `mail.example.com`       |
| `<MAIL_IP>`       | Public IPv4 of the mail server                      | `203.0.113.10`           |
| `<SERVER_FQDN>`   | The `DOMAIN_FQDN` from `.env` (postfix HELO/EHLO)   | `mail.example.com`       |
| `<DKIM_SELECTOR>` | DKIM selector generated by manager-api              | `dkim_2026_05`           |

`<MAIL_HOST>` and `<SERVER_FQDN>` can be the same host or different. What
matters is that `PTR(<MAIL_IP>)` resolves back to `<SERVER_FQDN>` (FCrDNS), not
to `<MAIL_HOST>`.

## TL;DR : the 4 records to publish

At your DNS provider, on the zone for `<DOMAIN>` :

| Type | Name                          | Value                                                                                       | Proxy / TTL |
|------|-------------------------------|---------------------------------------------------------------------------------------------|-------------|
| MX   | `@`                           | `<MAIL_HOST>` priority `10`                                                                 | DNS only    |
| TXT  | `@`                           | `v=spf1 mx ip4:<MAIL_IP> -all`                                                              | Auto        |
| TXT  | `<DKIM_SELECTOR>._domainkey`  | `v=DKIM1; k=rsa; p=<base64-public-key>` (value returned by manager-api on domain creation)  | Auto        |
| TXT  | `_dmarc`                      | `v=DMARC1; p=quarantine; rua=mailto:dmarc_reports@<DOMAIN>; ruf=mailto:dmarc_reports@<DOMAIN>; fo=1; adkim=r; aspf=r` | Auto |

Plus **one record at the IP owner** (typically the hosting provider, not the DNS
provider) :

| Type | Where  | Value                                |
|------|--------|--------------------------------------|
| PTR  | IP owner (OVH / Hetzner / AWS / ...) | `<MAIL_IP>` resolves back to `<SERVER_FQDN>` |

## Why each record exists

- **MX** tells the rest of the internet "for mail to `*@<DOMAIN>`, connect to
  `<MAIL_HOST>` on port 25". Priority 10 is conventional ; if you ever add a
  backup MX, give it priority 20.
- **SPF** authorizes which sending IPs are allowed for `<DOMAIN>`. `mx` covers
  every host declared in the MX records, `ip4:<MAIL_IP>` is the explicit fallback
  in case the MX target changes. `-all` is a hard fail : anything not listed is
  rejected.
- **DKIM** publishes the public half of the keypair opendkim uses to sign every
  outbound mail with `d=<DOMAIN>; s=<DKIM_SELECTOR>`. The private half stays on
  the server in `volumes/opendkim/keys/<DOMAIN>/<DKIM_SELECTOR>.private`.
- **DMARC** tells receivers what to do when SPF or DKIM fail to align with the
  `From:` header. `p=quarantine` sends mismatches to spam ; switch to `p=reject`
  after a week of clean reports. `rua` / `ruf` are reporting endpoints (aggregate
  and forensic).
- **PTR** is the reverse mapping for the sending IP. Gmail and Outlook check
  Forward-Confirmed reverse DNS (FCrDNS) : `<SERVER_FQDN>` must have an A record
  that points to `<MAIL_IP>`, and `<MAIL_IP>` must have a PTR that resolves back
  to `<SERVER_FQDN>`. Mismatch = mail in spam, period.

## Step-by-step

### 1. Publish MX, SPF and DMARC (do this first)

You can publish these three before the domain even exists in the server's DB ;
they don't need anything from manager-api.

**Cloudflare** (illustrative, the UI varies between providers) :
1. DNS → Records → Add record
2. MX
   - Name : `@` (or leave blank for the root)
   - Mail server : `<MAIL_HOST>`
   - Priority : `10`
   - Proxy status : **DNS only** (grey cloud, required - MX cannot be proxied)
3. TXT (SPF) on `@`
   - Content : `v=spf1 mx ip4:<MAIL_IP> -all`
4. TXT (DMARC) on `_dmarc`
   - Content : `v=DMARC1; p=quarantine; rua=mailto:dmarc_reports@<DOMAIN>; ruf=mailto:dmarc_reports@<DOMAIN>; fo=1; adkim=r; aspf=r`

> **Warning** : a domain can only carry ONE SPF (one TXT starting with `v=spf1`).
> If a SPF already exists (e.g. set by your previous mail provider), merge the
> mechanisms instead of adding a second record. Two SPFs make every receiver
> reject the domain wholesale.

### 2. Set up the reverse DNS (PTR)

At the IP owner. PTR config lives outside the DNS zone of `<DOMAIN>`.

- **OVH** : Bare Metal / VPS / Public Cloud panel → IP → Reverse DNS → set to
  `<SERVER_FQDN>`.
- **Hetzner** : Console → Server → Networking → reverse DNS.
- **AWS EC2** : open a support ticket from the EC2 console (you can't set PTR
  yourself by default), provide `<SERVER_FQDN>`.
- **Self-hosted (own ASN)** : update the reverse zone yourself.

Verify :

```bash
dig +short -x <MAIL_IP>
# should output : <SERVER_FQDN>.
```

### 3. Create the domain in manager-api

The DKIM key is generated by opendkim, the value you publish at the DNS provider
comes from the API response.

Get an access token first (see [INSTALL.md](INSTALL.md) section 5) :

```bash
TOKEN=$(curl -s -X POST http://127.0.0.1:4003/api/v1/auth/login \
  -H 'content-type: application/json' \
  -d '{"email":"root@example.com","password":"YourRootPassword"}' \
  | jq -r .access_token)
```

Create the domain :

```bash
curl -s -X POST http://127.0.0.1:4003/api/v1/domains \
  -H "authorization: Bearer $TOKEN" \
  -H 'content-type: application/json' \
  -d '{"name":"example.com"}'
```

Response (shape) :

```json
{
  "domain": { "id": 1, "name": "example.com", ... },
  "dns": [
    {
      "type": "MX",
      "name": "@",
      "value": "mail.example.com",
      "priority": 10
    },
    {
      "type": "TXT",
      "name": "@",
      "value": "v=spf1 mx ip4:203.0.113.10 -all"
    },
    {
      "type": "TXT",
      "name": "dkim_2026_05._domainkey",
      "value": "v=DKIM1; k=rsa; p=MIGfMA0GCSqGSIb3DQEBAQUAA4GNADCBiQKBgQDi..."
    },
    {
      "type": "TXT",
      "name": "_dmarc",
      "value": "v=DMARC1; p=quarantine; rua=mailto:dmarc_reports@example.com; ..."
    }
  ]
}
```

### 4. Publish the DKIM record

Copy the `value` of the DKIM entry (everything after `v=DKIM1; k=rsa; p=`) into
a TXT record at your DNS provider :

- Name : `<DKIM_SELECTOR>._domainkey` (e.g. `dkim_2026_05._domainkey`)
- Type : TXT
- Content : the full `v=DKIM1; k=rsa; p=...` string

Some DNS providers split long TXT records over 255-char chunks automatically ;
others want you to do it manually with quoted segments. Cloudflare handles it
for you transparently.

### 5. Verify with dig

From the server (or any host) :

```bash
# MX must resolve to <MAIL_HOST>, which must resolve to <MAIL_IP>
dig +short MX example.com
dig +short A mail.example.com

# SPF
dig +short TXT example.com

# DKIM
dig +short TXT dkim_2026_05._domainkey.example.com

# DMARC
dig +short TXT _dmarc.example.com

# Reverse
dig +short -x 203.0.113.10
```

All four DNS lookups should return non-empty results matching what manager-api
gave you. DNS propagation is usually a few minutes on Cloudflare (TTL Auto =
5 min) ; longer at some registrars.

### 6. Send a test mail

Create a mailbox for the new domain (via Swagger at `/api/doc`, the `users`
section, or curl `POST /api/v1/users`). Then send a test from any external
account to `<that-mailbox>@example.com` and check :

```bash
docker compose logs -f postfix
docker compose logs -f dovecot
```

For outbound deliverability scoring, use `https://www.mail-tester.com` :
1. They give you a temporary address like `test-xyz@mail-tester.com`.
2. Send from `your-mailbox@example.com` to that address.
3. Open the result page. Aim for **10/10**. Anything below 8/10, fix the
   warnings before going live (usually a missing PTR or a too-loose DMARC).

## DMARC tightening roadmap

1. **Day 1 to 7** : `p=quarantine`. Receivers send aggregate reports to `rua`.
   Read them (or use a parser like postmaster.google.com) to confirm 100% of
   your legitimate mail aligns.
2. **Day 8+** : switch to `p=reject` for full protection. Now spoofed senders
   pretending to be `@<DOMAIN>` are dropped, not just spammed.

```
v=DMARC1; p=reject; rua=mailto:dmarc_reports@<DOMAIN>; ruf=mailto:dmarc_reports@<DOMAIN>; fo=1; adkim=r; aspf=r
```

If you want strict alignment (subdomain `s=` mechanism = exact match instead of
organizational match), use `adkim=s; aspf=s`. Keep `r` (relaxed) unless you know
exactly why you want strict.

## Removing a domain

```bash
curl -s -X DELETE http://127.0.0.1:4003/api/v1/domains/<id> \
  -H "authorization: Bearer $TOKEN"
```

Then delete the MX / SPF / DKIM / DMARC records at the DNS provider. The DKIM
private key in `volumes/opendkim/keys/<DOMAIN>/` is **not** deleted automatically
on purpose - you might want to keep it around for a while if you ever want to
reactivate the domain with the same selector.
